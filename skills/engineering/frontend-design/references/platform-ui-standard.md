# Cross-platform UI design standard

Adopt Apple HIG for shared design principles and for native iOS, iPadOS, and macOS interfaces. Use Fluent guidance for Windows GUI, Material 3 and Android guidance for Android apps, and WCAG 2.2 AA for Web accessibility. Apply the actual host platform's controls, units, and system behavior, including in cross-platform frameworks. Record applicable sources and project-specific decisions in the existing design or task record. [Apple HIG](https://developer.apple.com/design/human-interface-guidelines) · [WCAG 2.2](https://www.w3.org/TR/WCAG22/)

## Typography, spacing, and layout

| Target | Typography | Layout and spacing |
|---|---|---|
| iOS and iPadOS | Use system text roles with Dynamic Type. At the default Large setting, size/leading in pt includes Large Title 34/41, Title 1 28/34, Title 2 22/28, Body 17/22, and Footnote 13/18. Let content wrap and rows grow as text scales. | Follow system guides, margins, and safe areas. Adapt iPad to available window space and multitasking. Aim for button hit regions of at least 44 × 44 pt. [Typography](https://developer.apple.com/design/human-interface-guidelines/typography) · [Layout](https://developer.apple.com/design/human-interface-guidelines/layout) · [Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons) |
| macOS GUI | Apple recommends a default text size of 13 pt. Use system font roles for menus, labels, window titles, and tooltips. | Follow native conventions for windows, menus, toolbars, and sidebars. Support resizing and keyboard shortcuts for frequent actions. Keep critical controls reachable when the bottom of a window extends below the screen. [Typography](https://developer.apple.com/design/human-interface-guidelines/typography) · [Layout](https://developer.apple.com/design/human-interface-guidelines/layout) · [Designing for macOS](https://developer.apple.com/design/human-interface-guidelines/designing-for-macos) |
| Windows GUI | Use Fluent roles. Size/line height in epx includes Caption 12/16, Body 14/20, Body Large 18/24, Subtitle 20/28, and Title 28/36. | XAML uses 4 epx increments for fixed dimensions, margins, and padding. Microsoft recommends 12 epx gutters below 640 epx of window width and 24 epx at larger widths. Map these roles to theme tokens in other GUI frameworks and verify in the actual window. [Typography](https://learn.microsoft.com/windows/apps/design/signature-experiences/typography) · [Alignment and spacing](https://learn.microsoft.com/windows/apps/design/layout/alignment-margin-padding) |
| Android App | Use Material 3 display, headline, title, body, and label roles. Set font sizes in sp and test system font scaling. | Use dp for layout, an 8 dp grid and 4 dp for finer spacing, and touch targets of at least 48 × 48 dp. Adapt to the actual window size class, including 600 and 840 dp width boundaries where applicable. Account for bars, cutouts, and the keyboard through window insets. [Material 3](https://developer.android.com/develop/ui/compose/designsystems/material3) · [Grid](https://developer.android.com/design/ui/mobile/guides/layout-and-content/grids-and-units) · [Targets](https://developer.android.com/develop/ui/compose/accessibility/api-defaults) · [Window classes](https://developer.android.com/develop/adaptive-apps/guides/use-window-size-classes) · [Insets](https://developer.android.com/develop/ui/views/layout/edge-to-edge) |
| Web | Use approved project tokens. When defining a new scale, start with body 16/24, secondary text 14/20, section heading 20/28, and page title 28/36 in CSS px or relative equivalents. | Start with spacing steps of 4, 8, 12, 16, 24, 32, and 48 CSS px or relative equivalents. Set breakpoints where content needs reflow. Support 200% text resizing and vertical content reflow at a width equivalent to 320 CSS px, subject to WCAG exceptions. [Text resizing](https://www.w3.org/TR/WCAG22/#resize-text) · [Reflow](https://www.w3.org/TR/WCAG22/#reflow) |

The Web scale and spacing steps are project defaults. Use each platform's own units. Use type and alignment to show hierarchy, and keep gaps within groups smaller than gaps between groups. Preserve access to primary actions as content grows. Store values in theme or token files and document their roles in DESIGN.md or its equivalent. See [Design system](design-system.md) and [Layout and scroll](layout-scroll.md).

## Components and interaction

- **Navigation.** Use tabs for top-level destinations, toolbars for actions on the current content, and sidebars for complex hierarchies. Preserve navigation state when switching sections. Keep destinations accessible as the layout changes. [Tab bars](https://developer.apple.com/design/human-interface-guidelines/tab-bars) · [Layout](https://developer.apple.com/design/human-interface-guidelines/layout)
- **Actions and dialogs.** Make the most likely action visually distinct and give custom buttons pressed feedback. Use a sheet or its platform equivalent for short tasks tied to the current context. Offer undo for common reversible deletion. Confirm uncommon irreversible deletion. Label actions by the result they produce. [Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons) · [Alerts](https://developer.apple.com/design/human-interface-guidelines/alerts) · [Sheets](https://developer.apple.com/design/human-interface-guidelines/sheets) · [Undo](https://developer.apple.com/design/human-interface-guidelines/undo-and-redo)
- **Forms, search, and permissions.** Reduce repeated input. Use reasonable defaults and selection controls where suitable. Label fields and put actionable correction messages near the input. Show search scope when it affects results. Ask for needed permissions when the user invokes the relevant feature and explain the purpose. [Entering data](https://developer.apple.com/design/human-interface-guidelines/entering-data) · [Writing](https://developer.apple.com/design/human-interface-guidelines/writing) · [Search](https://developer.apple.com/design/human-interface-guidelines/search-fields) · [Privacy](https://developer.apple.com/design/human-interface-guidelines/privacy)
- **Loading and recovery.** Use measurable progress when reliable and an activity indicator otherwise. Give distinct feedback for first-use empty states, no search results, loading failures, and access denial. Provide a recovery action when one is available. Teach through the task when onboarding is needed. [Progress](https://developer.apple.com/design/human-interface-guidelines/progress-indicators) · [Loading](https://developer.apple.com/design/human-interface-guidelines/loading) · [Feedback](https://developer.apple.com/design/human-interface-guidelines/feedback) · [Onboarding](https://developer.apple.com/design/human-interface-guidelines/onboarding)
- **Color, materials, and motion.** Keep color meanings consistent and pair meaningful color with another cue. Check light, dark, and increased contrast where supported. Use materials to communicate depth and motion to explain changes. Respect reduced-motion preferences. [Color](https://developer.apple.com/design/human-interface-guidelines/color) · [Materials](https://developer.apple.com/design/human-interface-guidelines/materials) · [Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)
- **Accessibility and localization.** Cover relevant touch, pointer, keyboard, and assistive technology paths. Provide understandable labels, visible focus in logical order, and accessible status feedback. Check long text, font scaling, locale formats, and supported reading directions. On Web, use WCAG AA text contrast of 4.5:1 for normal text and 3:1 for large text, subject to exceptions. Web pointer targets generally require 24 × 24 CSS px or a qualifying exception such as spacing. [Apple Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility) · [Right to left](https://developer.apple.com/design/human-interface-guidelines/right-to-left) · [WCAG contrast](https://www.w3.org/TR/WCAG22/#contrast-minimum) · [WCAG target size](https://www.w3.org/TR/WCAG22/#target-size-minimum)

For specialized features, consult the relevant official topic, including charts, drag and drop, file management, notifications, and multiple windows. [Apple Patterns](https://developer.apple.com/design/human-interface-guidelines/patterns) · [Apple Components](https://developer.apple.com/design/human-interface-guidelines/components)

## Acceptance on the final build

1. Before implementation, record the actual platform and entry point, applicable rules, affected states, user action, and expected observable result for each required check. For a keyboard-operated dialog, verify focus stays inside while open and returns to the opener when closed.
2. Verify the final build through the real entry point. On Web, check affected viewport sizes, text resizing, keyboard, and scroll behavior in a browser. For desktop GUI, check relevant window sizes, display or text scaling, menus, and keyboard in the actual window. For mobile, check affected orientations, large text, insets, the soft keyboard, and touch. Include permission, offline, error, and recovery paths when the change affects them.
3. Record the final revision or build, device or viewport, action, expected and observed outcome, and evidence. Rerun affected checks after input changes. When a required check lacks passing evidence, begin the final reply with 「验收未完成」 and keep the Issue in progress or blocked.
