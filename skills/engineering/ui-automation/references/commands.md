# Commands

## Windows desktop

For an interactive task, start `desktop-task --hwnd <decimal> --pid <integer>` with stdin open. It starts one capsule before binding and emits a `ready` record after verified focus. Send one JSON operation per line and read one response before deciding the next step:

- `{"op":"goal","goal":"<objective>","completion":"<visible condition>","region":{...}}` runs the read-only Jev loop within one approved rectangle in the bound window. Only that crop is sent to Jev. Supply optional `stages` for different crops or window handoffs. Each stage supplies a `name`, an `instruction`, and an approved `region` in the same rectangle format as a click target. Optional `candidates` selects choice mode, otherwise Jev locates the named control. Set `verify:true` on the final stage. Use `size:{width,height}` to withhold the crop if geometry changes, `guardRegion` for scoped click validation, and `windowTitle` for an exact same-process window handoff.
- A `fallback` event supplies the current observation and screenshot to the caller. Send `{"op":"resume-goal","observation":"<token>","target":{...}}` for one guarded click, or `"verified":true` for an observed completion condition. Use `{"op":"refresh-goal"}` to refresh the observation or `{"op":"cancel-goal"}` to stop. The goal result includes timings, followed by the CLI's final status after cleanup.
- Jev checks vision availability once per decision session using a synthetic image before transmitting any task crop. If the check fails, the task uses the fallback path. The check uses the same network environment as the task. Launch from the environment that has the intended HTTPS proxy settings.
- `{"op":"capture"}` returns a base64 PNG and token to an image-capable caller. The task only refocuses after foreground loss. Inspect the screenshot before acting.
- `{"op":"click","observation":"<token>","target":{"x":0,"y":0,"width":1,"height":1,"description":"Visible control"}}` uses the latest screenshot. The optional `action` uses the visual typing format below.
  For a read-only navigation click blocked by verified unrelated animation, supply an optional `guardRegion` in the same rectangle format. Include the full control and surrounding UI that identifies it. The region must extend at least eight image pixels beyond every side of the click target. Only this region is compared for pixel stability. Window identity, geometry, focus, hit testing, and freshness checks still apply. Typing and batch actions retain full-window validation.
- `{"op":"wait"}` leaves the capsule showing wait while the operator waits for a result. Use capture again to check the current state.
- `{"op":"batch","observation":"<token>","steps":[...]}` performs 2–5 disjoint actions selected from one image. Each step has `target` and optional `action`. Intermediate steps can type into visible fields. Clicks, submits, and sensitive input are allowed in the final step. Review a new screenshot if a step fails or changes the screen. A partial result includes the number of fully completed steps. Verify visible state before retrying.
- `{"op":"wait-change","timeoutMs":10000}` polls window pixels inside the task. Only a changed frame is encoded and delivered. A timeout returns `changed:false`. A changed frame may show an intermediate application state.
- `{"op":"resume-capture","userConfirmed":true}` resumes capture after the owner clears or confirms credential entry.
- `{"op":"finish","outcome":"pass"}` finishes a manual task after the operator verifies the visible result. Other outcomes are `fail`, `unverified`, and `stopped`. Finish, EOF, cancellation and the 15-minute limit detach the session and release in-memory observations.

Capture, action, wait-change and finish events include elapsed time. Action results also report screenshot-to-dispatch time and the native guard and input durations.

### Optional Jev click

Use this only for read-only navigation when the full captured window can be sent to TypeSafe. A capture token, a short goal and two to five click regions from that image are required. Provide only navigation candidates. The operation accepts no typing, submit action or arbitrary model-generated coordinates.

```json
{"op":"jev-click","observation":"<token>","question":"Which control opens the leaderboard?","candidates":[{"x":30,"y":200,"width":55,"height":40,"description":"Leaderboard"},{"x":30,"y":260,"width":55,"height":40,"description":"Charts"}]}
```

The CLI reads `TYPESAFE_API_KEY` or the current user's DPAPI-encrypted `%LOCALAPPDATA%/ui-automation/typesafe-key.dpapi`. It attempts Jev once per frame with a two-second HTTP deadline. It submits only a declared region through the existing click guard when Jev returns a valid candidate with confidence at least 0.95. An `action` event includes `provider:"jev"` and `jevMs`. After a `jev-fallback`, inspect the same screenshot and choose the next action as usual. After a guard error, capture again. Continue to verify the resulting screen and final outcome locally.

Use `sessions` with `discoverDesktop:true`, then `prepare --kind desktop --hwnd <decimal> --pid <integer>`. Focus with `act` using `{session,action:{type:"focus"}}`. Capture a fresh temporary image using `visual-observe --session <id> --out <new-PNG-file>`. Send the exact image token and bounded target to `visual-click`. To click, type into the selected field and optionally press Enter, include `action:{type:"type",text:"...",submit:true}`. For a password, supply `secretEnv` instead of `text`. After the owner confirms the login or clears the password, resume with `act` using `{session,action:{type:"resume-capture",userConfirmed:true}}`. The desktop path supports fresh screenshots and guarded input. Structured targets, case replay and structured assertions apply to browsers.

All commands return JSON. Exit 0 means the command completed (or a test passed), 1 means failed assertions, 2 means unavailable/unverified/error/stopped. Actions explicitly return `actionExecuted:true, goalVerified:false`; only a fresh assertion verifies a goal.

First build the independent user runtime with .NET 10 SDK: `node <skill>/scripts/ui-automation.mjs prepare --runtime --dotnet <dotnet.exe> --register`. The publish output is self-contained; subsequent commands do not depend on the build SDK. Registration is HKCU Chrome/Edge only, permits the manifest's stable extension ID and starts no system service. Node requires 20+. Runtime/cache/config/evidence default to `%LOCALAPPDATA%/ui-automation`; `UI_AUTOMATION_HOME` overrides the location.

Add `--laya` to publish the independent local decision worker. `--packages <dir>` and `--package-source <feed>` optionally select its package cache/feed; exact transitive versions and hashes are locked. `--runtime-dir <dir>` and `--registration-dir <dir>` select explicit publish/Native Messaging locations when required by the environment. Updating a loaded extension requires its popup's Reload bridge button; a page refresh alone does not reload the service worker. Reconnect to the current runtime after a rebuild.

Prepare weights separately with `prepare --model-source <verified-export-dir>`. This verifies the five fixed ONNX/config/tokenizer hashes in [model-manifest.json](model-manifest.json), copies them to ui-automation's own cache, and records that directory. The original directory is read-only. No runtime download or Python process occurs. The export provenance is the pinned official [SDK/exporter](https://github.com/NandhaKishorM/laya/tree/6f0496f797dc7127265d62e1543a62de507d943c/laya-dotnet) and [checkpoint](https://huggingface.co/convaiinnovations/laya-multilingual/tree/1720e3e3357cfe1e281542e223f8273b0890ca34); weights are not included in Git. A different export/hash is rejected, even if its supplied manifest claims the same provenance. Fresh export tooling is a development prerequisite, not part of daily UI control. `run --model-dir <dir>` can explicitly select a verified directory; otherwise it uses the prepared cache.

Load the returned `loadUnpacked` folder in `chrome://extensions` (or `edge://extensions`), developer mode → Load unpacked. This uses the normal profile. Open the bridge popup and choose Connect; select the exact tab via `sessions` then `prepare --kind browser --connection <id> --tabId <integer>`. Extension permissions are debugger, nativeMessaging, tabs and storage. Chrome displays its normal debugging indicator. DevTools or user detach can invalidate the session; prepare again after reconnect.

`sessions --request <json>` discovers connected tabs. With `{"discoverDesktop":true}` it also lists visible windows; bind with `prepare --kind desktop --hwnd <decimal> --pid <integer>`. Sessions expire when broker/extension/target exits. Explicitly prepare a modal dialog's own window; stop detaches the session and preserves the app.

`doctor` diagnoses connected runtime. `observe --session <id>` yields `id`, completeness, identity and nodes (role/name/value/state/bounds/context/id). `act --request <json>` takes `{session,observation,action}`. `validate --request <json>` takes `{session,assertion:{target:{name,role},property:"value",equals:"literal"}}` and observes afresh. `stop --session <id>` invalidates a session. `run --request <case.json> --out <local-dir>` executes a case; Ctrl+C cancels. `inspect --run <run-dir>` verifies source/tool/artifact digests.

`visual-observe --session <id> --out <new-PNG-file>` saves the current bound surface without overwriting an existing file and returns a visual token plus absolute `image.path` and pixel dimensions. `visual-click --request <json>` takes `{session,observation,target:{x,y,width,height,description}}`; coordinates refer to that exact image. Read [visual fallback](visual.md) before selecting a region or dispatching a visual click.

Browser actions use observed target IDs. JSON requests contain no executable shell fragments.

Browser `prepare` accepts `allowOrigins` (exact origins), either an existing `tabId` or a task-created `createUrl`, optional `allowedTabIds`, and explicit `trackPopups:true`. `focus` restores a minimized window, selects the bound tab and verifies foreground. With the connected native host it briefly opens a bridge-owned marker tab in that exact window, obtains native HWND/PID foreground readback, restores the target tab, removes the marker and verifies Chrome state again. User page titles/content stay untouched. Structured browser input recovers foreground before probing its observed target. Browser actions also include `navigate`/`newTab` (`url`), `switchTab` (`tabId` already declared/discovered within scope), `scrollIntoView`, `files` (absolute local file list), and `dialog` (`accept`, optional prompt `text`). A frame target includes its observed `context`; both same-process frames and OOPIFs retain their own CDP session. `stop` preserves tabs by default; `closeCreated:true` only removes tabs recorded as task-created in this extension lifetime. After reload, uncertain ownership is preserved.

An explicit `focus` action uses `{session,observation,action:{type:"focus"}}` without a target ID. Success adds `diagnostics.foreground` with `verified:true`; desktop includes literal `hwnd/pid`, browser includes `tabId/windowId`, native readback and `markerRemoved:true`. It remains `goalVerified:false`. Native activation restores only minimized desktop windows and preserves maximized state, tries ordinary activation, then a private paired ALT input assist if needed. Held modifiers, expired/stopped sessions, ambiguous marker identity or denied input produce an error. This helper changes no system focus setting or permanent topmost state. Reobserve after failed activation; use a modal dialog's own session. Visual clicks retain their strict foreground/freshness checks and never repair an old screenshot by silently focusing.

Browser observations can narrow a selector or frame context. Incomplete observations cannot act.

Browser secretEnv values are resolved at dispatch and redacted from later observations. Browser capture is refused after sensitive input.

The broker listens on a Windows current-user-only named pipe. Local processes running as the same user are trusted. The native host checks the exact invoking extension origin. Per-build pipes prevent version cross-talk. No remote listening socket or cookie API is exposed.
